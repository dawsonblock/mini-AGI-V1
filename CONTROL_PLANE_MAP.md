# Campaign 3B.3 — Priority 1: control-plane map

Status: **mapped and classified from the tree, with the limits of the
method stated.** Generated by `scripts/analysis/control_plane_map.py`;
the machine-readable result is `CONTROL_PLANE_MAP.json`.

The priority asks for "one authoritative control plane" and the
elimination of "duplicate authority and unresolved trust boundaries".
Neither is actionable until it is known *which* authority is
authoritative. The tree carries several generations of authority code.
This maps them by reachability rather than by reading.

## Method, and what it cannot decide

The tool finds every module that mentions authority-like symbols
(`Authority`, `AuthorityRegistry`, `assert_authorized`,
`AuthorizedLaunchRecord`, `qualify`, `admit`, `revocation`, `trust_root`,
…) and classifies each by reachability from the repository's own entry
points (the CLI, `scripts/**`, the release and qualification tools):

| class | meaning |
|---|---|
| **LIVE** | reachable by import from an entry point |
| **SERVICE-ENTRYPOINT** | has a `main()` / `__main__` guard — **operator-launched, invisible to an import graph** |
| **TEST-ONLY** | reachable only from the test tree |
| **ORPHAN** | neither |

The middle class exists because the first version of this map did not
have it, and without it the production service read as "test-only" —
which would have been a false and alarming claim. **A static import
graph proves reachability, not deployment.** Whether a
SERVICE-ENTRYPOINT module is the path production actually runs cannot be
settled from the tree alone, and this map does not pretend otherwise.

## Finding 1 — four competing promotion/qualification implementations

The tree carries **four** implementations of promotion or qualification
that no live path reaches:

1. `dream_rsi_governed.promotion` + `.qualification` + `.activation`
2. `kvcontinual.execution.durability.promotion_authority` (336 lines)
3. `minagi.rc14.qualification` (224 lines)
4. `minagi.egai.authority` (119 lines)

The live one is `minagi.v161.authority` (299 lines). **This is the
duplicate authority the priority names, now identified with evidence.**

### The sharpest form of the defect

The control plane is **singular at the registry level**: `AuthorityRegistry`
and `AuthorityLedger` are defined in exactly one place,
`minagi/v161/authority.py`, and nowhere else. That is verified, not
assumed — a test asserts no second module defines either class.

What is *not* singular is the **vocabulary**. Competing classes carry the
names a reader would search for:

| class | module | reachable? |
|---|---|---|
| **`PromotionAuthority`** | `dream_rsi_governed.promotion` | **ORPHAN** |
| `PromotionAuthorization` / `RollbackAuthorization` | `kvcontinual…promotion_authority` | ORPHAN |
| `QualificationEngineRC14` | `minagi.rc14.qualification` | ORPHAN |

**A reader looking for "the promotion authority" finds
`dream_rsi_governed.promotion.PromotionAuthority` — a class with exactly
that name — and it is not the one that counts.** The live promotion path
is `scripts/promote.py` → `minagi.v161.authority`.

So the defect is not that the code exists; it is that the code is
*indistinguishable* from the authority that counts.

## Finding 2 — a module named `control_plane` is orphaned

`minagi.v16.control_plane` (133 lines) has no import path and no entry
point. A module carrying the name of the thing this priority is trying
to establish is not reachable from anywhere. Either it is superseded and
should be retired explicitly, or something should be using it and is
not. **Both readings are defects; the tree does not say which.**

## Finding 3 — the isolation chain sits outside static reachability

`minagi.runtime.supervisor` is LIVE and is imported by
`minagi.v161.trusted_launcher`, so the activation lifecycle is wired.
But the **launch and isolation chain** —
`service` → `nsjail_executor` → `worker_launch_broker` /
`isolation_preflight` / `worker_executor` / `worker_isolation` — is
reachable **only** through `minagi.runtime.service`, which is
SERVICE-ENTRYPOINT.

Consequences, stated precisely:

- It is **not** dead code: `service.py` has `main()` and a `__main__`
  guard, so an operator runs it directly.
- It is **not** verifiable from the tree: nothing in the repository
  establishes that the production deployment runs *this* entry point
  rather than the `kvcontinual` gateway (`macos/run_gateway.sh` execs
  `kvcontinual.continual.mac_api:app`) or the native `qw3` binary
  (`docker/Dockerfile.cuda` `ENTRYPOINT`).

**This is the unresolved trust boundary.** The Phase G runtime defects
the review identified live in this chain, and the chain's *reachability
in production* is asserted nowhere. Hardening those files is necessary
but not sufficient: the boundary also needs the deployment path to be
pinned and verifiable.

## What this enables, and what it does not

**Enables:** a definite answer to "which authority is authoritative"
(`minagi.v161.authority`), an evidence-backed list of what is *not* part
of the control plane, and a precise statement of the one boundary static
analysis cannot close.

**Does not:** justify deleting anything. An ORPHAN donor tree kept for
provenance is legitimate — the point is to stop treating it as an
authority, not to remove it. Retiring those modules is a decision with
provenance consequences and is proposed, not taken.

## Priority 1 actions — status

### 1. Signed control-plane manifest — **DONE**

`CONTROL_PLANE_MANIFEST.json`, generated by
`scripts/analysis/control_plane_manifest.py` and signed with Ed25519. It
declares the live authority, the nine live control-plane modules with
each one's role, the seven superseded implementations, and the
deployment entry point — and **refuses to emit** if the declared sets
disagree with what the map actually finds. The answer to "which authority
is authoritative" is now a signed artifact rather than something only
available by reading.

`manifest_sha256` is bound into the source envelope, so a change that
adds a competing authority, removes the live one, or moves the deployment
path changes the digest.

### 2. Superseded implementations marked — **DONE**

All seven carry an in-module notice naming the live authority, the live
path, and their successor:

> **NOT THE LIVE CONTROL PLANE.** … The single live authority is
> `minagi.v161.authority` … Do not import this module into a live path
> without recording that decision.

Nothing was deleted: these are retained for provenance and for import-probe
coverage, and the import probe still passes 36/36. A test asserts that
every module the manifest calls superseded both stays unreachable **and**
carries the notice — so the ambiguity cannot silently return.

### 3. `minagi.v16.control_plane` resolved — **DONE (marked superseded)**

It is the v16.0 converged qualification control plane, superseded by
`minagi.v161.converged_evidence` (`ConvergedEvidenceBundleV160` →
`ConvergedEvidenceBundleV161`). It is imported by its own package
`__init__` and covered by the import probe, but no live path reaches the
package. Marked rather than deleted, with the successor named.

### 4. Deployment path — **DECLARED, NOT VERIFIED**

This is the one action the tree cannot finish, and it is now stated as
such rather than left as an inference. `minagi.runtime.service` is
declared the deployment entry point in the manifest, with an explicit
`NOT VERIFIED` status, because nothing in this repository establishes
that production runs it rather than the `kvcontinual` gateway
(`macos/run_gateway.sh` execs `kvcontinual.continual.mac_api:app`) or the
native `qw3` binary (`docker/Dockerfile.cuda` ENTRYPOINT).

What the tree *can* establish, it now does: a test proves the entry point
is launchable (`python3 -m minagi.runtime.service --help` exits 0). What
it cannot establish is that a deployment invokes it — and pinning that
belongs with the runtime-security branch, where the deployment is
defined.
